Both Builder Track questions ask what the tool FOUND. One is now answered with a
real run. One is not, and cannot be from outside.


TOOL 1, ACCESSIBILITY: SOLVED. NOTHING NEEDED FROM YOU.

There is no public Salesforce product called "Accessibility Expert Skill", but
Salesforce does publish accessibility expert tooling, and we found it, installed
it and ran it.

  Where it lives   The Salesforce DX MCP server, npm package @salesforce/mcp,
                   in its "lwc-experts" toolset. Public, installable, GA.
  Tools used       guide_component_accessibility
                   run_lwc_accessibility_jest_tests
  What they set up Sa11y, Salesforce's own axe-core accessibility matcher.

WHAT WE RAN AND WHAT IT FOUND

  12 component states audited, 131 axe checks passed, 0 WCAG violations,
  against the 100-rule "extended" preset rather than the 64-rule default.

  Two real defects found and both fixed and deployed:

  1. Signed video in the console had no captions and, worse, no explanation of
     why. Auto-captioning is the one thing this product promises never to do,
     so every video now carries a description saying so out loud to the person
     who cannot watch it.

  2. LWC1057. The emergency form's textarea used an attribute that does nothing,
     so closing an escalation left the previous emergency's words on screen. On
     the one screen that produces a telephone number. Fixed.

  Full write-up: docs/A11Y-SA11Y-REPORT.md
  Raw findings:  docs/a11y-sa11y-findings.json
  Re-run it:     npm run test:a11y

Q1 on Devpost has been rewritten around these findings.
