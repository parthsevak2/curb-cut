We ran our own audit continuously and hard: 333 automated accessibility checks against the six LIVE pages on every build, plus 28 contrast checks computed from the design tokens in both themes, and 16 reading-level checks. The build fails on any of them.

The findings that mattered most, though, came from doing what a static scan cannot: driving the deployed page with a real browser and reading its accessibility tree.

WHAT THAT FOUND, AND WHAT WE DID

1. The claim code never took focus. Every asynchronous update on /ask moves focus to its heading: results, draft, sent. The standing-preference save set tabindex on the heading and then never called focus(). That is the single moment where a six-character code is shown once and cannot be recovered, and a screen-reader user was left exactly where they were. The one person who most needed telling was not told. FIXED: the code panel is now a real heading and takes focus, pinned by a static check.

2. 46 unnamed <section> elements across six pages. An unnamed section is announced as an anonymous "region", so somebody navigating the home page by landmark heard "region" twelve times with nothing to tell them apart. FIXED: every section now points at its own heading, held by a live-page check.

3. A 22px target on the footer mail link, under WCAG 2.5.8's 24x24. Inline links in running text are exempt, but this one sits alone and is the only way to reach a human by email, so it is a target and is now sized like one.

4. Status regions had no aria-atomic, so a rewritten message could be announced in fragments.

5. The focus ring is 5.7:1 against the page ground but only 2.7:1 against a dark filled button beside it. It now carries a second pale ring so the indicator survives whatever it lands on.

WHAT WE KEPT, AND WHY

Deaf, blind, hard of hearing and wheelchair user are deliberately never redacted from what a person writes, even though we strip volunteered medical conditions. They are identity and function, not medical detail; they are how people describe themselves; and the interpreter routing reads them. Stripping how somebody names themselves would be its own insult. A check fails the build if any of them enters the condition list.

We also kept a deliberately plain Visualforce surface rather than a JS framework, so the page renders for older assistive technology.

A FINDING WE DISPROVED

Our first browser pass appeared to show 26 controls with no focus indicator. That would have been alarming. But :focus-visible does not match a programmatic .focus(). So we drove it with real Tab presses and got 3px solid rgb(11,87,199) at 3px offset, exactly as designed. The test method was wrong, not the site. We report that because a defect we did not have is worse to claim than one we missed.

CHECKS MOST TEAMS DO NOT HAVE

- Reading level is measured on every surface. The page somebody uses while struggling reads at grade 5.8, and the build fails above its ceiling.
- One auditor fails the build if an error message blames the person reading it or leaves them with no next step.
- One fails if our own copy tells somebody to send a word the system does not actually answer. It exists because for months our copy said "reply OFF" and nothing routed it.

THE GAP WE HAVE NOT CLOSED

No screen-reader user has tested this. Every claim above is machine-verified or browser-verified, which is not the same thing as a person using it. A browser is not a person. One session with somebody who uses a screen reader daily would be worth more than the next five features, and we say so on the evidence page rather than letting the numbers imply otherwise.
